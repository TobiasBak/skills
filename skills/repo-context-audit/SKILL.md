# Repository context audit

Identify which repository context adds useful information and which merely constrains competent work. Keep authoritative knowledge easy to retrieve without turning it all into instructions.

An audit authorizes inspection and recommendations. An explicit request to improve context authorizes edits within that scope, not new repository policy or unrelated code changes. Existing governing instructions remain active until an authorized change replaces them.

## Instructions worth loading

Compare instructions with the active model, host guidance, tools, and current task. Use available evidence to distinguish direct duplication from a judgment about expected model behavior. A rule being correct, prudent, or once useful does not establish that it adds value now.

Distinguish:

- Chosen collaboration and priorities, such as the working relationship the user wants. These need not be justified as error prevention, but not every preference belongs in every session.
- Local facts and obligations the agent would otherwise miss, including actual authority boundaries and consequential repository contracts. A possible hazard does not create a prohibition or approval requirement.
- Corrective coaching for behavior the model or host may already handle. Keep it only for a concrete unmet need, not an imaginable mistake or an old model's habit.

Judge each instruction's contribution and scope. Do not treat commit conventions, generated files, testing, or any other topic as a mandatory category to fill. A documented preference can remain retrievable knowledge without becoming an always-loaded rule.

Removing unnecessary coaching does not require a replacement reviewer, hook, or benchmark. Transferring responsibility for a real obligation is different: preserve that obligation and verify the replacement according to its consequences.

## Repository knowledge and retrieval

Look for competing authorities, implementation copied into prose, and useful rationale or domain knowledge that is hard to find. Code owns implemented behavior; documentation can preserve intent, rationale, external contracts, and shared terminology. Follow the repository's document conventions rather than imposing a layout or purpose from a filename.

When assessing retrieval, try searches drawn from real tasks, errors, or domain terms and inspect whether they reach the owning artifacts. Improve the route that fails, not an abstract naming score. Do not infer missing knowledge from one narrow search or turn a context audit into an unsolicited code refactor.

## Recommendations and authorized edits

Show material findings with their locations, why they matter, and the proposed treatment. For changes to governing instructions, show the exact wording or diff and distinguish retiring unnecessary coaching from changing policy. Proceed when the user has already authorized the scope and direction.

Deletion can be the whole improvement. Relocation, new documentation, and mechanical enforcement need their own reason. Recommend no change when the current context serves the work.

After edits, check affected authority and retrieval routes. Rerun representative searches for retrieval claims and check links when destinations change. If authorized work changes code behavior, verify the affected contract through focused public-interface or real-use checks; compilation alone does not establish behavior. Report the changes and any material uncertainty without prescribing a fixed report format.
